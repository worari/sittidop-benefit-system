## 1. ขอบเขตและพจนานุกรมข้อมูล

### 1.1 ขอบเขตระบบ (System Scope)

ระบบจัดเก็บและบริหารข้อมูลกำลังพลรายบุคคล เพื่อใช้คำนวณ ประมาณการ และติดตามสิทธิสวัสดิการ 5 ด้านหลัก (รักษาพยาบาล, การศึกษา, ที่พักอาศัย, เงินเพิ่มพิเศษ, เงินช่วยเหลือครอบครัว) รองรับกำลังพลทุกชั้นยศ ทุกเหล่า และทุกประเภทกำลังพล

### 1.2 พจนานุกรมข้อมูล (Data Dictionary)

| # | ฟิลด์ข้อมูล | ชนิดข้อมูล | กติกาตรวจสอบ (Validation Rule) | ชั้นข้อมูล (Classification) | หมายเหตุ |
|---|---|---|---|---|---|
| D-01 | เลขประจำตัวกำลังพล (Military ID) | String(10) | ตัวเลข 10 หลัก, Unique, ห้ามว่าง | ลับ (Confidential) | Primary Business Key |
| D-02 | ชื่อ-สกุล | String(200) | อักษรไทย/อังกฤษ, ห้ามว่าง, แยกคำนำหน้า-ชื่อ-สกุล | ส่วนบุคคล (PII) | รองรับการเปลี่ยนชื่อ (เก็บประวัติ) |
| D-03 | ยศ (Rank) | Master Reference | ต้องมีในทะเบียนยศ ทบ. (พล.อ. → พลฯ + อส.ทพ.) | ภายใน (Internal) | เก็บเป็นประวัติ Temporal พร้อมวันที่มีผล |
| D-04 | เหล่า (Corps/Branch) | Master Reference | ทะเบียนเหล่า เช่น ร., ม., ป., ช., ส., สพ., พธ., ขส., พ. | ภายใน | Master Data มีรหัสมาตรฐาน |
| D-05 | ตำแหน่ง (Position) | Master Reference + Text | อ้างอิงอัตราตำแหน่ง (อฉก./อจย.) | ภายใน | ผูกกับหน่วยและวันที่มีผล |
| D-06 | หน่วย (Unit) | Master Reference | ต้องมีในผังหน่วย (Unit Hierarchy) | ภายใน | โครงสร้างต้นไม้ ทบ. → กองทัพภาค → กรม → กองพัน |
| D-07 | ประเภทกำลังพล | Enum | นายทหารสัญญาบัตร / นายทหารประทวน / พลทหารกองประจำการ / อส.ทพ. / พนักงานราชการ / ลูกจ้าง | ภายใน | กำหนดชุดสิทธิที่มีสิทธิได้รับ |
| D-08 | วันที่บรรจุ (Appointment Date) | Date | ≤ วันปัจจุบัน, พ.ศ./ค.ศ. แปลงถูกต้อง | ภายใน | ฐานคำนวณอายุราชการ |
| D-09 | อายุราชการ (Service Years) | Computed Decimal(5,2) | **คำนวณอัตโนมัติ** จากวันบรรจุ + เวลาทวีคูณ ห้ามกรอกเอง | ภายใน | แยกปกติ / ทวีคูณ / รวม |
| D-10 | เงินเดือน (Salary) | Decimal(15,2) | > 0, อยู่ในช่วงบัญชีเงินเดือนของระดับ/ขั้น | ลับ | เก็บประวัติ Temporal |
| D-11 | สิทธิรักษาพยาบาล | Entitlement Record | สถานะสิทธิ + เพดาน + ผู้มีสิทธิร่วม (คู่สมรส บุตร บิดามารดา) | ลับ + ข้อมูลอ่อนไหว | ข้อมูลสุขภาพ = Sensitive PII ตาม PDPA ม.26 |
| D-12 | สิทธิการศึกษา | Entitlement Record | สถานะสิทธิ + ทุน/ค่าเล่าเรียนบุตร + เงื่อนไขอายุ/สถานะการศึกษาบุตร | ลับ | ผูกทะเบียนบุตร |
| D-13 | สิทธิที่พักอาศัย | Entitlement Record | สถานะ: มีบ้านพัก / รอจัดสรร (คะแนน+ลำดับคิว) / รับค่าเช่าบ้าน | ภายใน | ผูกทะเบียนบ้านพักและบัญชีรอ |
| D-14 | เงินเพิ่มพิเศษ | Entitlement Record (หลายรายการ) | รหัสประเภท (พ.ช.ท., พ.ส.ร., ค่าเสี่ยงภัย ฯลฯ) + อัตรา + ช่วงวันที่มีผล | ลับ | ตรวจกับตารางอัตราใน Rule Engine |
| D-15 | เงินช่วยเหลือครอบครัว | Entitlement Record | ประเภท + จำนวน + ผู้รับ (สมาชิกครอบครัว) + งวดจ่าย | ลับ + PII ครอบครัว | รวมกรณี MA-2000 ตามเอกสารออกแบบระบบ |

## 2. Functional Requirements

> ระดับความสำคัญ: **M** = Must Have, **S** = Should Have, **C** = Could Have (MoSCoW)

### 2.1 กลุ่มทะเบียนกำลังพล (FR-PER)

| รหัส | ความต้องการ | ระดับ | เกณฑ์การยอมรับ (Acceptance Criteria) |
|---|---|---|---|
| FR-PER-01 | ระบบต้องบันทึก แก้ไข ค้นหา ข้อมูลกำลังพลครบ 15 ฟิลด์ตามพจนานุกรมข้อมูล (D-01…D-15) | M | สร้าง/แก้/ค้นหาได้ครบทุกฟิลด์, ฟิลด์บังคับต้องไม่ว่าง |
| FR-PER-02 | เลขประจำตัวกำลังพลต้องไม่ซ้ำ และตรวจรูปแบบ 10 หลักก่อนบันทึก | M | บันทึกซ้ำถูกปฏิเสธพร้อมข้อความแจ้งภาษาไทย |
| FR-PER-03 | ยศ เหล่า ตำแหน่ง หน่วย ประเภทกำลังพล ต้องเลือกจาก Master Data เท่านั้น (ห้ามพิมพ์อิสระ) | M | Dropdown/Autocomplete จากทะเบียนกลาง, ค่านอกทะเบียนถูกปฏิเสธ |
| FR-PER-04 | ระบบต้องคำนวณอายุราชการอัตโนมัติจากวันที่บรรจุ + เวลาราชการทวีคูณ และห้ามผู้ใช้แก้ค่าโดยตรง | M | ค่าอายุราชการเป็น Read-Only, คำนวณถูกต้องเทียบชุดทดสอบ 100% |
| FR-PER-05 | ระบบต้องเก็บประวัติการเปลี่ยนแปลง ยศ / หน่วย / ตำแหน่ง / เงินเดือน แบบ Temporal (วันที่มีผลเริ่ม-สิ้นสุด) | M | เรียกดูข้อมูล ณ วันที่ใดก็ได้ (Point-in-Time Query) |
| FR-PER-06 | ระบบต้องรองรับการโยกย้ายหน่วยและเลื่อนยศโดยอ้างอิงเลขที่คำสั่ง และคำนวณผลกระทบต่อสิทธิที่ผูกพัน | M | เมื่อบันทึกคำสั่ง ระบบสร้างรายการปรับปรุงสิทธิที่ได้รับผลกระทบอัตโนมัติ |
| FR-PER-07 | ระบบต้องรองรับการนำเข้าข้อมูลกำลังพลจากไฟล์ Excel พร้อม Dry-run Validation และรายงานข้อผิดพลาดระบุแถว/คอลัมน์ | S | ไฟล์ที่มีข้อผิดพลาดไม่ถูกบันทึก, ดาวน์โหลด Error Report ได้ |
| FR-PER-08 | ระบบต้องจัดการทะเบียนครอบครัว (คู่สมรส บุตร บิดามารดา ทายาท) ผูกกับกำลังพล | M | เพิ่ม/แก้สมาชิกครอบครัวพร้อมเอกสารอ้างอิงและสัดส่วนการรับสิทธิ |

### 2.2 กลุ่มสิทธิและสวัสดิการ (FR-BEN)

| รหัส | ความต้องการ | ระดับ | เกณฑ์การยอมรับ |
|---|---|---|---|
| FR-BEN-01 | ระบบต้องคำนวณสิทธิสวัสดิการรายบุคคลครบ 5 ด้าน (รักษาพยาบาล การศึกษา ที่พักอาศัย เงินเพิ่มพิเศษ เงินช่วยเหลือครอบครัว) ตามยศ ประเภทกำลังพล และอายุราชการ | M | ผลคำนวณตรงกับ Golden Test Cases ที่ กพ.ทบ. รับรอง 100% |
| FR-BEN-02 | เงื่อนไขและอัตราสิทธิทุกรายการต้องกำหนดผ่าน Rule Engine (Rule as Data) มีเวอร์ชันและวันที่มีผล โดยไม่ต้องแก้โปรแกรม | M | ADMIN แก้อัตราแล้วมีผลกับการคำนวณใหม่ทันที, การคำนวณเดิมยังอ้างเวอร์ชันเดิม |
| FR-BEN-03 | สิทธิรักษาพยาบาลต้องตรวจเพดานต่อปีต่อคน และครอบคลุมผู้มีสิทธิร่วม (คู่สมรส บุตร บิดามารดา) | M | คำขอเกินเพดานถูกแจ้งเตือนและตัดยอดอัตโนมัติ |
| FR-BEN-04 | สิทธิการศึกษาต้องตรวจสถานะการศึกษาและอายุบุตรก่อนอนุมัติ และรองรับอัตราพิเศษบุตรผู้เสียชีวิต/ทุพพลภาพ | M | บุตรพ้นเกณฑ์ระบบปฏิเสธพร้อมเหตุผล |
| FR-BEN-05 | สิทธิที่พักอาศัยต้องมีระบบคะแนน บัญชีรอ (Queue) และการจัดสรรที่ตรวจสอบย้อนได้ | S | ลำดับคิวคำนวณจากเกณฑ์คะแนนที่ประกาศ, ทุกการจัดสรรมี Audit Trail |
| FR-BEN-06 | เงินเพิ่มพิเศษต้องผูกกับตำแหน่ง/ภารกิจ และคำนวณอัตโนมัติรายเดือนตามตารางอัตรา | M | ยอดรวมรายเดือนตรงกับตารางอัตราทุกรายการ |
| FR-BEN-07 | เงินช่วยเหลือครอบครัวต้องระบุผู้รับ งวดจ่าย และสถานะจ่าย พร้อมตรวจสถานะสิทธิ (Active/Suspended/Terminated) | M | ทุกงวดจ่ายมีหลักฐานอ้างอิงและผู้อนุมัติ |
| FR-BEN-08 | ระบบต้องออกหนังสือรับรองสิทธิรายบุคคล (PDF/DOCX) พร้อม QR Code ตรวจสอบความถูกต้อง | S | เอกสารตรงรูปแบบราชการ, สแกน QR แล้วตรวจสถานะได้ |
| FR-BEN-09 | กำลังพลต้องดูสิทธิของตนเองได้แบบ Self-Service (อ่านอย่างเดียว) | S | เห็นเฉพาะข้อมูลตนเอง, PII ถูก Mask ตามนโยบาย |

### 2.3 กลุ่มรายงานและงบประมาณ (FR-RPT)

| รหัส | ความต้องการ | ระดับ | เกณฑ์การยอมรับ |

## 3. Non-Functional Requirements

> อ้างอิงมิติคุณภาพตาม ISO/IEC 25010

| รหัส | มิติ | ข้อกำหนด | ตัวชี้วัด (Measurable Target) |
|---|---|---|---|
| NFR-01 | **Performance** | เวลาตอบสนองหน้าจอค้นหา/แสดงข้อมูลกำลังพล | ≤ 2 วินาที ที่ P95 |
| NFR-02 | Performance | เวลาคำนวณสิทธิรายบุคคลครบ 5 ด้าน | ≤ 5 วินาที ต่อราย |
| NFR-03 | Performance | การประมวลผลชุด (Batch) เช่น คำนวณเงินเพิ่มรายเดือนทั้งหน่วย | ≥ 10,000 ราย/ชั่วโมง |
| NFR-04 | **Scalability** | รองรับทะเบียนกำลังพล | ≥ 500,000 ราย (รวมพ้นราชการ/ทายาท) |
| NFR-05 | Scalability | ผู้ใช้งานพร้อมกัน (Concurrent Users) | ≥ 1,000 sessions โดยไม่เสื่อมประสิทธิภาพเกิน 20% |
| NFR-06 | **Availability** | ความพร้อมใช้งานเวลาราชการ (07:00–18:00) | ≥ 99.5% ต่อเดือน |
| NFR-07 | Availability | RPO / RTO | RPO ≤ 15 นาที, RTO ≤ 4 ชั่วโมง |
| NFR-08 | **Reliability** | ความถูกต้องการคำนวณสิทธิเทียบชุดทดสอบรับรอง | 100% (Zero Tolerance) |
| NFR-09 | Reliability | ธุรกรรมการเงิน/สิทธิเป็น Transaction สมบูรณ์ (ACID) และ Batch เป็น Idempotent | รันซ้ำไม่เกิดรายการซ้ำ 100% |
| NFR-10 | **Usability** | UI ภาษาไทยราชการ รองรับผู้ใช้ที่ไม่ชำนาญเทคโนโลยี | งานหลักสำเร็จโดยไม่ต้องอบรมซ้ำ ≥ 80% (UAT Usability Test) |
| NFR-11 | Usability | รองรับหน้าจอ Desktop และ Tablet | Responsive ≥ 768px |
| NFR-12 | **Maintainability** | กฎ/อัตราแก้ไขได้โดยไม่ Deploy ใหม่ (Rule as Data) | เปลี่ยนอัตรามีผลภายใน 5 นาที |
| NFR-13 | Maintainability | Test Coverage ตรรกะคำนวณสิทธิ | ≥ 90% |
| NFR-14 | **Portability** | ติดตั้งด้วย Container บนเครื่องแม่ข่ายภายใน ทบ. (On-Premise) | Docker/K8s ไม่ผูกกับ Cloud เฉพาะราย |
| NFR-15 | **Compatibility** | Browser ที่รองรับ | Chrome/Edge เวอร์ชันปัจจุบัน −2 |
| NFR-16 | **Auditability** | ทุกธุรกรรมตรวจสอบย้อนหลังได้ | Audit Log ครบ Who-What-When-Why 100%, เก็บ ≥ 10 ปี |
| NFR-17 | **Data Retention** | เก็บข้อมูลกำลังพลและสิทธิตลอดอายุราชการ + ตามระเบียบงานสารบรรณ | นโยบายเก็บ-ทำลายเป็นลายลักษณ์อักษร |

### 4.2 ความเสี่ยงคงเหลือ (Residual Risk) ที่ต้องยอมรับโดยผู้บริหาร

- ความคลาดเคลื่อนของข้อมูลย้อนหลังก่อนวันที่ระบบเริ่มใช้ (Historical Data Accuracy) — บริหารโดยกำหนด "วันตัดยอดข้อมูล" อย่างเป็นทางการ
- การพึ่งพาเอกสารรับรองจากหน่วยงานภายนอกที่ยังเป็นกระดาษ

## 5. Data Governance

### 5.1 โครงสร้างธรรมาภิบาลข้อมูล (Governance Structure)

| บทบาท | ผู้รับผิดชอบ (เสนอ) | หน้าที่ |
|---|---|---|
| **Data Governance Committee** | รอง จก.กพ.ทบ. เป็นประธาน | อนุมัตินโยบาย, ตัดสินข้อขัดแย้งด้านข้อมูล |
| **Data Owner** | ผอ.กองที่กำกับทะเบียนแต่ละกลุ่ม | รับผิดชอบความถูกต้องและการอนุญาตใช้ข้อมูลในกลุ่มของตน (กำลังพล/สิทธิ/การเงิน) |
| **Data Steward** | นายทหารกำลังพลหน่วยที่ได้รับแต่งตั้ง | ดูแลคุณภาพข้อมูลประจำวัน, แก้ไขข้อมูลตามคำร้อง |
| **Data Custodian** | ผู้ดูแลระบบสารสนเทศ | ดูแลเทคนิค: สำรองข้อมูล, สิทธิเข้าถึง, เข้ารหัส |
| **DPO (เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล)** | ผู้ที่หน่วยแต่งตั้งตาม PDPA | กำกับการคุ้มครองข้อมูลส่วนบุคคล, รับเรื่องร้องเรียน |

### 5.2 การจำแนกชั้นข้อมูล (Data Classification)

| ชั้น | ข้อมูล | การควบคุม |
|---|---|---|
| **ลับมาก (Secret)** | ข้อมูลรวมที่สะท้อนกำลังรบ เช่น ยอดกำลังพลรายหน่วย+ที่ตั้ง | เข้าถึงเฉพาะ HQ_OFFICER ขึ้นไป, ห้าม Export โดยไม่อนุมัติ |
| **ลับ (Confidential)** | เงินเดือน, เลขบัตรประชาชน, บัญชีธนาคาร, ข้อมูลสุขภาพ/ความพิการ | เข้ารหัสคอลัมน์ + Masking + Audit ทุกการเข้าถึง |
| **ส่วนบุคคล (PII)** | ชื่อ-สกุล, ที่อยู่, ข้อมูลครอบครัว | ควบคุมตาม PDPA, ใช้ตามวัตถุประสงค์ที่ประกาศ |
| **ภายใน (Internal)** | ยศ, เหล่า, ตำแหน่ง, หน่วย, ทะเบียนกฎ | ผู้ใช้ที่ Login แล้วตามบทบาท |

### 5.3 คุณภาพข้อมูล (Data Quality Rules)

| มิติ | เกณฑ์ | ตัวชี้วัดเป้าหมาย |
|---|---|---|
| Completeness | ฟิลด์บังคับ (D-01…D-10) ครบถ้วน | ≥ 99.5% ของระเบียน |
| Uniqueness | เลขประจำตัวกำลังพล/เลขบัตรประชาชนไม่ซ้ำ | 100% |
| Validity | ค่าตาม Master Data และช่วงที่กำหนด | ≥ 99.9% |
| Consistency | เงินเดือนสอดคล้องบัญชีถือจ่ายของยศ/ระดับ | ตรวจอัตโนมัติทุกคืน รายการขัดแย้งเข้าคิว Steward |
| Timeliness | คำสั่งโยกย้าย/เลื่อนยศบันทึกภายใน | 5 วันทำการหลังคำสั่งมีผล |
| Accuracy | สุ่มตรวจกับเอกสารต้นฉบับรายไตรมาส | ความคลาดเคลื่อน ≤ 0.5% |

### 5.4 วงจรชีวิตข้อมูล (Data Lifecycle)

1. **สร้าง** — จากการบันทึกโดย Steward หรือ Import (ผ่าน Validation เท่านั้น)
2. **ใช้งาน** — ตามบทบาทและ Data Scope; ทุกการอ่านข้อมูลลับถูกบันทึก Log
3. **เก็บรักษา** — ข้อมูลกำลังพล: ตลอดอายุราชการ + 10 ปีหลังพ้นราชการ; ธุรกรรมการเงิน/สิทธิ: ≥ 10 ปี; Audit Log: ≥ 10 ปี (WORM)
4. **โอนย้าย/แลกเปลี่ยน** — ต้องมี MOU และช่องทางเข้ารหัสเท่านั้น
5. **ทำลาย** — ตามระเบียบงานสารบรรณและมติคณะกรรมการ พร้อมบันทึกการทำลาย

### 5.5 Master Data Management

- ทะเบียนกลาง: ยศ, เหล่า, ตำแหน่ง/อัตรา, ผังหน่วย, ประเภทกำลังพล, ตารางอัตราเงินเพิ่ม — มีเจ้าของข้อมูล (Data Owner) รายทะเบียน
- การแก้ Master Data ต้องผ่านอนุมัติและมีวันที่มีผล (Effective Dating) — ห้ามแก้ทับของเดิม

## 6. Security Requirements

| รหัส | หมวด | ข้อกำหนด |
|---|---|---|
| SEC-01 | Authentication | Login ด้วยบัญชีบุคคล (ห้ามบัญชีร่วม), รหัสผ่าน ≥ 12 ตัวอักษรผสม, บังคับเปลี่ยนทุก 90 วัน, ล็อกเมื่อผิด 5 ครั้ง |
| SEC-02 | Authentication | **MFA บังคับ** สำหรับบทบาทที่อนุมัติสิทธิ/การเงิน และผู้ดูแลระบบ |
| SEC-03 | Session | JWT อายุ ≤ 60 นาที + Refresh Rotation, Logout อัตโนมัติเมื่อไม่ใช้งาน 15 นาที, Session เดียวต่อผู้ใช้ (Configurable) |
| SEC-04 | Authorization | RBAC 8 บทบาท + Data Scope ตามผังหน่วย, ตรวจสิทธิ์ที่ Service Layer ทุกครั้ง (ไม่พึ่ง UI), Deny by Default |
| SEC-05 | Segregation of Duties | ผู้บันทึก ≠ ผู้อนุมัติ; ผู้อนุมัติสิทธิ ≠ ผู้อนุมัติจ่ายเงิน; การแก้เลขบัญชีธนาคารต้อง Four-Eyes |
| SEC-06 | Data at Rest | เข้ารหัสคอลัมน์ลับ (เลขบัตร, บัญชีธนาคาร, เงินเดือน, ข้อมูลสุขภาพ) ด้วย AES-256-GCM, กุญแจเก็บแยกใน Secret Manager, หมุนกุญแจรายปี |
| SEC-07 | Data in Transit | TLS 1.3 ทุกช่องทาง รวมภายในเครือข่าย, ปิด Protocol/Cipher เก่า |
| SEC-08 | Application | Input Validation ทุก Endpoint, ป้องกัน OWASP Top 10, Security Headers + CSP, Rate Limiting, Idempotency-Key ธุรกรรมเงิน |
| SEC-09 | Infrastructure | แยก Network Zone (DMZ/App/DB), DB ไม่เปิดสู่ภายนอก, Hardening ตาม CIS Benchmark, Patch รายเดือน |
| SEC-10 | Monitoring | ส่ง Security Event เข้า SIEM, แจ้งเตือน Login ผิดปกติ/การ Export จำนวนมาก/การเข้าถึงนอกเวลาราชการ |
| SEC-11 | Testing | Vulnerability Scan รายไตรมาส, Penetration Test ก่อน Go-Live และรายปี, แก้ช่องโหว่ Critical ภายใน 7 วัน |
| SEC-12 | Backup/DR | สำรองข้อมูลเข้ารหัส, ทดสอบ Restore รายไตรมาส, DR Drill รายปี (RPO 15 นาที / RTO 4 ชั่วโมง) |
| SEC-13 | Personnel | ผู้ดูแลระบบต้องผ่านการตรวจสอบความไว้วางใจ, ทบทวนสิทธิผู้ใช้รายไตรมาส, เพิกถอนสิทธิภายใน 24 ชม. เมื่อย้าย/พ้นหน้าที่ |
| SEC-14 | Compliance | สอดคล้อง ISO/IEC 27001, พ.ร.บ.ไซเบอร์ 2562 (ระบบอาจเข้าข่าย CII), นโยบายความมั่นคงปลอดภัยสารสนเทศ ทบ. |

## 7. Privacy Requirements

> อ้างอิง พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA) — ข้อมูลสุขภาพ/ความพิการเป็น **ข้อมูลอ่อนไหวตามมาตรา 26**

| รหัส | ข้อกำหนด | รายละเอียด |
|---|---|---|
| PRV-01 | ฐานการประมวลผล (Lawful Basis) | จัดทำ Record of Processing Activities (RoPA): ข้อมูลกำลังพลใช้ฐาน **หน้าที่ตามกฎหมาย/ภารกิจรัฐ (ม.24)**; ข้อมูลสุขภาพ/ความพิการใช้ข้อยกเว้น **ม.26** เพื่อสิทธิสวัสดิการตามกฎหมาย พร้อมมาตรการคุ้มครองเฉพาะ |
| PRV-02 | Privacy Notice | แจ้งวัตถุประสงค์ ประเภทข้อมูล ระยะเวลาเก็บ และสิทธิของเจ้าของข้อมูล ต่อกำลังพลและสมาชิกครอบครัว ณ จุดเก็บข้อมูล |
| PRV-03 | Data Minimization | เก็บเฉพาะฟิลด์ที่จำเป็นต่อการคำนวณสิทธิ (ตามพจนานุกรมข้อมูล) ห้ามเก็บเผื่อ |
| PRV-04 | Purpose Limitation | ห้ามใช้ข้อมูลนอกวัตถุประสงค์สวัสดิการ เช่น ห้ามใช้ข้อมูลสุขภาพประกอบการพิจารณาโยกย้าย เว้นแต่มีกฎหมายรองรับ |
| PRV-05 | สิทธิเจ้าของข้อมูล (DSR) | ช่องทางให้กำลังพล: เข้าถึง/ขอสำเนา, ขอแก้ไขให้ถูกต้อง, คัดค้าน/ขอลบ (เท่าที่ไม่ขัดหน้าที่ตามกฎหมาย) — ตอบสนองภายใน 30 วัน พร้อมบันทึกคำขอทุกรายการ |
| PRV-06 | Masking & Pseudonymization | เลขบัตรประชาชนแสดงแบบ Mask ทุกหน้าจอยกเว้นบทบาทที่จำเป็น; ชุดข้อมูลสำหรับวิเคราะห์/พยากรณ์งบประมาณต้องผ่าน Anonymization/Aggregation |
| PRV-07 | ข้อมูลบุคคลที่สาม | ข้อมูลคู่สมรส บุตร บิดามารดา ทายาท ถือเป็นเจ้าของข้อมูลแยกราย — ต้องแจ้ง Privacy Notice และคุ้มครองเท่ากำลังพล |
| PRV-08 | ผู้เยาว์ | ข้อมูลบุตรที่ยังไม่บรรลุนิติภาวะ ประมวลผลผ่านผู้ใช้อำนาจปกครอง ตาม ม.20 |
| PRV-09 | Retention & Erasure | เก็บตามตารางใน Data Governance (ข้อ 5.4); พ้นกำหนดแล้วลบ/ทำให้ไม่สามารถระบุตัวตน พร้อมหลักฐานการทำลาย |
| PRV-10 | Data Breach Response | แผนตอบสนองเหตุละเมิดข้อมูล: ประเมิน-ควบคุมภายใน 24 ชม., แจ้ง สคส. ภายใน 72 ชม. หากมีความเสี่ยงต่อเจ้าของข้อมูล, แจ้งเจ้าของข้อมูลกรณีความเสี่ยงสูง |
| PRV-11 | Third-Party/Processor | ผู้รับจ้างพัฒนา/บำรุงรักษาต้องลง Data Processing Agreement (DPA) และเข้าถึงได้เฉพาะข้อมูลจำลอง (Masked Data) ในสภาพแวดล้อมทดสอบ |
| PRV-12 | DPIA | จัดทำ Data Protection Impact Assessment ก่อน Go-Live เนื่องจากมีข้อมูลอ่อนไหว (สุขภาพ/ความพิการ) ในปริมาณมาก |
